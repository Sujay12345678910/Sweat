# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A barebones GPS pace tracker Android app, purpose-built for a single device target: the Innioasis G1 (Android 8.1). Pure Android SDK only, with one deliberate exception: a JSch-based SFTP client for manual NAS backup (see Architecture, "NAS sync").

User-facing app name is **Sweat** (`android:label`, `applicationId "com.sweat"` in `app/build.gradle`). The Java package (`com.runtracker`), source folder layout, and this repo/directory name are intentionally left as `RunTracker` — the rename only touched what's user-visible and the installed package identity (done specifically so this build wouldn't collide with an older `com.runtracker`-signed install already on the device; see `app/build.gradle` for the full reasoning). Don't "fix" this mismatch by renaming the Java package unless asked — it's deliberate, not leftover debt.

## Build & run

Requires a `local.properties` file pointing at the Android SDK (not checked in):
```
sdk.dir=/path/to/your/Android/Sdk
```

Installation is via sideloading over microSD (no Play Store, no ADB-only workflow assumed) — see README.md for the full device install steps if a task involves the install/distribution flow.

## Architecture

Two classes: `MainActivity` (UI only) and `LocationService` (a bound + foreground `Service`) — no fragments, no ViewModel/Compose. GPS handling, run-state tracking, and pace math live in `LocationService` via `LocationListener` callbacks; `MainActivity` binds to it, renders state via a small `UpdateListener` callback, and drives its own `Handler`-based timer loop by polling `LocationService.getElapsedMs()`.

The service split exists specifically so tracking survives the Activity being backgrounded: Android 8+ throttles/kills location updates for apps that aren't in the foreground, so `LocationService` promotes itself with `startForeground()`/an ongoing notification for the duration of an active run (`startTracking()`/`pauseTracking()`), independent of GPS acquisition (which starts as soon as location permission is granted, matching the original always-on-while-open behavior). If you're tempted to fold GPS handling back into `MainActivity` for simplicity, don't — that's the exact bug this fixed (tracking silently stopping in the background).

Key constraints that shape the code (keep these in mind when modifying):
- **Single target device**: `minSdkVersion`/`targetSdkVersion` are pinned to API 26/28 to match the G1 exactly. Don't add API calls that require higher API levels — this also means no `android:foregroundServiceType` manifest attribute (API 29+) on `LocationService`.
- **No dependencies**: `app/build.gradle` has zero library dependencies by design (small APK, low-resource device). Don't add Jetpack/AndroidX/third-party libraries without a strong reason — this includes avoiding `ArrayList`/boxed collections in hot paths (see the pace buffer below), and using `android.app.Notification.Builder`/`NotificationChannel` directly rather than `NotificationCompat`.
- **GPS pipeline**: `LocationManager.GPS_PROVIDER` only (no fused/network provider, no Play Services), owned by `LocationService`. Updates arrive via `onLocationChanged`, gated on `running`, and filtered for jitter (`GPS_MIN_DISTANCE_M` = 5m) and implausible speed between fixes (`MAX_PLAUSIBLE_SPEED_MPS`, applied against the actual elapsed time between fixes rather than a flat distance — a flat cap wrongly zeroes real distance after any multi-second GPS gap, since a gap covers more ground than a cap sized for the steady-state 2s interval). Fixes worse than `GPS_MAX_ACCURACY_M` are dropped entirely — not counted toward distance and not allowed to become the new baseline (`lastLocation`) either, since a noisy fix (common right at run start) would otherwise make the next good fix look like a jump and get discarded too.
- **Pace smoothing**: a fixed-size circular buffer (`paceBuffer`, `PACE_WINDOW = 5`) computes a moving average with no per-sample heap allocation — intentional given the constrained device. Preserve this pattern when touching pace logic.
- **Run state across pause/resume**: `elapsedMs` accumulates time across pause/resume cycles; `lastLocation` is deliberately nulled on pause to avoid a spurious distance jump when GPS drifts while stopped. `startTimeMs` bookkeeping (in `LocationService`) should stay consistent with this if changed.
- **Screen-on / GPS-always-on while foregrounded**: `MainActivity` sets `FLAG_KEEP_SCREEN_ON` and stays bound to `LocationService` for its whole lifecycle (bind in `onCreate`, unbind in `onDestroy` — not `onPause`/`onStop`) — the app is meant to be glanced at mid-run without unlocking, and rebinding on every foreground/background cycle would be unnecessary churn. Don't "fix" this into a lifecycle-scoped bind unless the product behavior is meant to change.
- **Foreground service lifecycle**: `startTracking()`/`pauseTracking()`/`resetTracking()` on `LocationService` control `startForeground()`/`stopForeground()`/`stopSelf()`. A run started via the Start button keeps going (GPS + notification) even if the Activity is destroyed (e.g. task swipe) — only Pause or Reset stop it. Keep that property when touching this lifecycle; it's what the background-tracking fix depends on.
- **Track points → GPX export**: `LocationService` records every accepted GPS fix during a run into parallel primitive arrays (`trackLat`/`trackLon`/`trackEle`/`trackTimeMs`, grown by doubling — same no-boxed-collections rationale as the pace buffer). On `resetTracking()`, if the run has ≥2 points, it's serialized to a `.gpx` file (via `android.util.Xml`, no library) under `getExternalFilesDir("gpx")` — deliberately *not* uploaded anywhere; the offline device can't assume connectivity, so GPX export + manual upload to Strava's website (which accepts GPX natively) was chosen over building OAuth/API upload code. No storage permission is needed since it's the app's own external files dir.
- **Touch lock + volume-key pause**: `MainActivity` disables `btnStartStop`/`btnReset`/`btnSync` (`setLocked(true)`) for the duration of an active run, to prevent accidental taps (pocket/armband) from pausing or resetting. The only way to pause while locked is a long-press on the physical Volume Down key (`onKeyLongPress`, `KEYCODE_VOLUME_DOWN`) — `onKeyDown` swallows Volume Down while locked so it doesn't also nudge media volume. This was chosen over trying to detect the screenshot-gesture chord (power+volume-down), which has no reliable public API. Keep `locked` in sync with `LocationService.isRunning()` wherever run state changes (`toggleRun`, `resetRun`, `syncButtonAndTimerWithServiceState`, `pauseFromVolumeKey`).
- **NAS sync is the one dependency exception**: `NasSync.java` uses the `com.github.mwiede:jsch` SFTP library (declared in `app/build.gradle`) because there's no SSH/SFTP client in the Android SDK — this is a deliberate, documented break from the zero-dependency rule, not an oversight. It's manual-trigger only (`btnSync`, never automatic) to preserve the offline-by-default design: the app never opens a network connection unless the user taps Sync. Connection details and the SSH private key are read from plain files under `getExternalFilesDir("nas")` (`nas_config.properties`, `id_rsa`) rather than baked into the app, so they can be changed via USB/microSD without a rebuild. Host-key verification is disabled (`StrictHostKeyChecking=no`) — acceptable for a personal home-LAN NAS, but a real MITM weakening if that threat model ever changes. Successfully uploaded `.gpx` files are moved into `gpx/uploaded/` so re-running Sync doesn't re-upload them.

## UI

`app/src/main/res/layout/activity_main.xml` is a single `LinearLayout`, dark theme, large-text stat readout (distance / pace / time / GPS accuracy) plus start/stop and reset buttons. Button drawables are in `res/drawable/btn_start.xml` / `btn_reset.xml`. No resource strings file — text is inlined in the layout XML and in `MainActivity.java` (`String.format` calls for distance/pace/time formatting).

The three stat readouts are deliberately not visually equal weight — pace is the primary glanceable metric, distance secondary, elapsed time tertiary: `tvPace` is largest (72sp) with a distinct heavy font (`sans-serif-black`) and the brand accent color (`#1DB954`, matching the start button); `tvDistance` is next (58sp, bold, default font, white); `tvTime` is smallest emphasis (52sp, `sans-serif-medium`, dimmed to `#DDDDDD`). Keep this ordering (pace > distance > time) if the readouts are touched again.
